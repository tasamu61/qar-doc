# 5 品質保証

AI を使うシステムは、**自分のコードを変えなくても、外部の都合で壊れる**ことがあります。
提供元の API の仕様、モデルの挙動、返事の書式は、予告なく変わります。
そこで、品質保証を **3 つの層**に分けています。

## 5.1 層 1：偽の AI による自動テスト（毎回）

| 項目 | 内容 |
|---|---|
| 目的 | **自分の変更で、壊れていないか**を確かめる |
| 方式 | 提供元を、決まった答えを返す偽物に差し替える。**外部への通信も課金もない** |
| 規模 | 40 件超。数秒で終わる |
| 対象 | 画面からの入口（入力の検証、セッション、利用制限）、固定質問の構造、提供元ごとの**返事の解析**（OpenAI の関数呼び出し、Gemini のテキスト、Groq のツール呼び出しなどの例を固定） |

**変更のたびに実行します。**

## 5.2 層 2：実際の AI による回帰テスト（定期）

| 項目 | 内容 |
|---|---|
| 目的 | **AI 側の仕様変更や不調**に、早く気づく |
| 方式 | 複数のテーマ × 複数の提供元で、**質問の生成 → 回答 → 結果の生成**を実際に呼ぶ |
| 記録 | 提供元ごとの、成功と失敗の件数と、失敗の内訳 |
| 例 | ツール呼び出しの引数が、JSON として成立しない形で返ってくる、といった失敗を、原因別に検出する |
| 注意 | 課金されるため、回数と頻度を決めて実行する |

この考え方を、小さく書き下ろしたものが[参考実装](../reference/qar_ref/evaluate.py)です。

## 5.3 層 3：変更の進め方

デグレ（壊してしまうこと）を避けるため、次の順で進めています。

1. **今の動きを、先にテストで固定する**（バグも含めて、現状のまま）。
2. **変更は小さく、1 つずつ**。変更のたびにテストを実行する。
3. **変更後のコードと、変更前のコードの両方に、同じテストを当てる。**
   変更前のコードで失敗するテストが、**意図して直した箇所だけ**であることを確認する。
4. 変えた点と理由、挙動が変わる点を、変更履歴に記録する。

## 5.4 テストの確かさ

テストが「通るだけ」になっていないかを、**変異テスト**で確認しています。
コードをわざと壊して（検証の無効化、順位の逆転、前処理の削除、許可リストの無効化）、テストが失敗することを確かめます。
[参考実装](../reference/README.md)で、同じ確認を再現できます。

## 5.5 セキュリティの確認も、同じ仕組みで

自己レビューで見つけた不備は、修正して終わりにせず、**再発を防ぐテストとして固定**しています。
（具体的な内容は、運用上の理由で公開していません。）
