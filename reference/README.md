# 参考実装（reference）

QARの設計の考え方を、**小さく書き下ろしたコード**で示したものです。
本番のコードではなく、**本番のコードは含みません**。標準ライブラリだけで動き、外部への通信はしません。

```
python -m unittest discover -s tests -t . -v     # テスト（32件）
python -m qar_ref.demo                           # 動作例
```

## 何を示しているか

| ファイル | 示していること | 関連する設計書の章 |
|---|---|---|
| `qar_ref/providers.py` | AI提供元の**差し替え口**と**許可リスト**。提供元の差は中に閉じ込め、名前からモジュールを動的に読み込まない。崩れ方を再現できる偽のAI | [4章](../docs/04-ai-integration.md) |
| `qar_ref/schema.py` | AIの返事の**取り出し・正規化・検証**。コードフェンス、JSONの連続、配列だけ、といった揺れを吸収し、`javascript:`などのURLを通さない | [4章](../docs/04-ai-integration.md) |
| `qar_ref/service.py` | 提供元の返事を、解析・検証してから使う**共通の層**。失敗を`parse`/`schema`に分類し、やり直しを設定できる | [4章](../docs/04-ai-integration.md) |
| `qar_ref/evaluate.py` | 提供元ごとの**成功率と失敗の内訳**を測る評価の仕組み | [5章](../docs/05-quality.md) |
| `qar_ref/scoring.py` | 2002年版の**積和スコア**を現代版の部品として再構成。**絶対条件**で先に絞り、順位は決定的に決める。LLMには順位を変えさせず、説明だけを頼む | [8章](../docs/08-2002-vs-now.md)、[9章](../docs/09-roadmap.md) |

## 動作例（`python -m qar_ref.demo` の出力）

> 下の成功率は**偽のAIによる数値**です。評価の仕組みを示すためのもので、実在のAIの成績ではありません。

```
■ 決定的なスコア計算（絶対条件: 5日以内・15万円以内）
  1位 沖縄  適合度=60  内訳={1: 24, 2: 36, 3: 0}
  2位 グアム  適合度=37  内訳={1: 22, 2: 15, 3: 0}
  3位 江ノ島  適合度=33  内訳={1: 30, 2: 3, 3: 0}
  除外 タヒチ（days<=5, cost<=150000）

■ 提供元ごとの成功率（3つの偽のAIで、崩れ方を再現）
提供元       段階              成功/試行     成功率  失敗の内訳
flaky-20  questions      79/100    79%  parse=12, schema=9
flaky-20  result         87/100    87%  parse=9, schema=4
flaky-50  questions      48/100    48%  parse=30, schema=22
flaky-50  result         56/100    56%  parse=32, schema=12
stable    questions     100/100   100%  -
stable    result        100/100   100%  -

■ 同じ条件で、失敗時に最大2回やり直す設定にすると
提供元       段階              成功/試行     成功率  失敗の内訳
flaky-20  questions      99/100    99%  schema=1
flaky-20  result        100/100   100%  -
flaky-50  questions      84/100    84%  parse=10, schema=6
flaky-50  result         83/100    83%  parse=12, schema=5
```

サンプルデータ（候補、日数、費用）は、説明のための架空のものです。
スコアの考え方は、[2002年版の資料](../archive/2002/outline.html)の例を現代版の形に置き換えています。

## テストの確かさについて

テストが「通るだけ」になっていないかを確かめるため、コードをわざと壊す変異テストを行いました
（URL検証の無効化、順位の昇順化、フェンス除去の削除、許可リストの無効化）。
いずれも、テストが失敗することを確認しています。
