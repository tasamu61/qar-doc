01 / 概要と結論

QARは、利用者に質問を提示して回答を収集し、希望に合う旅行先などを提案するWebアプリケーションである。現行版では推奨処理の中心をLLMに委ねている。

4AI提供元の選択肢
3主要POST API
7固定旅行質問

2002年版は独自の数値評価ロジックを核としたシステム。現行版は、質問の生成と回答からの提案生成を外部AIに依頼する設計へ転換した。ただし、現在のZIPではRAG/FAISSや独自スコアリングエンジンは実装として確認できない。

根拠：README.md、web_serv.py、texts/pharse.py、docs/KNOWN_ISSUES.md

02 / 実装アーキテクチャ

サーバは ALLOWED_LLMS = ("openai","google","groq","self") の許可リストを使い、importlib.import_module(f"{llm}_ai") で提供元モジュールを選択する。クライアント指定の任意モジュールを読み込まない設計になっている。

根拠：web_serv.py 12行付近、66–126行付近、framework/aop_session.py、各 *_ai.py

04 / データとインターフェース

API入力出力備考
GET /なしHTML＋署名付きCookieセッションIDを新規発行
POST /get_questionstheme, sendInstruction, aillm等{"questions":[...]}AI生成。selfは固定質問
POST /get_questions_travelJSON{"questions":[...]}旅行用固定7問
POST /get_resultanswer.theme、answer.answers、answer.aillm等{"result":[...]}想定提供元の戻り値を返却

質問の形式

{
 "questions": [
  {"id": 1,
   "text": "出発地は？",
   "type": "text",
   "choices": []}
 ]
}

type: single / multiple / text / text1

回答送信の形式

{
 "answer": {
  "theme": "旅行",
  "aillm": "openai",
  "sendInstruction": "",
  "answers": [
   {"question": "出発地は？",
    "answer": "横浜"}
  ]
 }
}

推薦結果は data.result をフロント側で map() し、destination などを使ってGoogle検索用URLを組み立てる。AIからの応答内容について、サーバ共通のJSONスキーマ検証は実装されていない。

根拠：static/vue_app.js、web_serv.py、texts/pharse.py、docs/KNOWN_ISSUES.md

提供元実装プロンプトと結果位置づけ
OpenAIopenai_ai.pyChat Completions API。functions/function_call形式を使用。モデル指定 gpt-4o-mini実装
Googlegoogle_ai.pygoogle.generativeai。コード上のモデル指定は gemini-3.6-flash。JSON解析失敗時の型が不統一実装稼働可否未検証
Groqgroq_ai.pyOpenAI互換HTTP API、モデル指定 openai/gpt-oss-20b。応答形式の揺れを複数パターンで解析実装
selfself_ai.py ＋ selfai_serv.pyhttp://localhost:8000/get_result へのHTTP要求。別サーバはスタブ実験・未完成

各モジュールに get_prompt_q、get_prompt_r、get_result を設ける設計だが、戻り値の型は辞書、文字列、タプルなどで統一されていない。これは将来のProviderインターフェース共通化候補。

根拠：各 *_ai.py、selfai_serv.py、docs/ARCHITECTURE.md

06 / セキュリティ・品質・運用

実装済みの防御

  • 許可リストによるAIモジュール選択
  • 署名付きCookieのセッションID
  • メモリ上の有効セッション照合
  • Flask-Limiterによる呼び出し制限
  • 旧資料のパス解決に safe_join を使用
  • APIキーを環境変数で取得

運用上の注意

  • セッションとレート制限はワーカー間で共有されない
  • AI応答の共通スキーマ検証がない
  • AIの異常応答時のエラー処理が不統一
  • ログに質問やプロンプトが残る
  • AIが生成するURLの真偽検証がない
  • 本番では環境変数 SEED が必須

テストの二層構成

テストファイルには、セッション、レート制限、提供元ごとのレスポンス解析、HTTPエラー、旧資料配信、パストラバーサル対策などの検証が含まれる。今回はテストコードの静的解析であり、外部APIへの接続試験や本番稼働確認は行っていない。

根拠：tests/、reg_test.py、reg_test2.py、framework/aop_session.py、docs/KNOWN_ISSUES.md

07 / 2002年版との対比

2002年版

決定的な評価・選択

質問・回答
→
評価値の計算
→
候補の順位付け

回答と候補の評価データを数値的に結びつける方式。評価根拠を追跡しやすい反面、評価データの設計・保守が必要。

現行版

LLMによる推奨生成

質問・回答
→
プロンプト
→
LLM提案

柔軟な自然言語解釈と提案文生成が可能。ただし、評価基準の固定、根拠提示、再現性は別途設計が必要。

今後の技術的な差別化として、2002年版の数値評価方式を再導入し、LLMは入力の解釈と説明生成を担う「ハイブリッド方式」が考えられる。ただし、これは現行ソースに実装済みの機能ではない。

根拠：static/doc/2002/ の旧資料、README.md、docs/KNOWN_ISSUES.md

08 / 課題・拡張案

機能このZIPでの確認結果資料上の扱い
Vue / Flaskによる質問・回答UI実装あり現行機能
OpenAI・Google・Groq切替実装あり。ただし外部サービスの現時点の稼働は未確認現行機能
独自LLMself向けスタブあり。独自モデル本体の完成は確認できない未完成
RAG / FAISS / 旅行データベース実行経路で確認できない構想
2002年式のスコア計算現行API処理で確認できない再導入候補
JSONスキーマによるAI応答検証共通検証なし改善候補
Redis等のセッション共有未実装改善候補

優先順位の提案

第一段階：Providerの戻り値・例外・タイムアウトの統一、JSON応答検証、実AI回帰テストの安定化。
第二段階：2002年版の評価方式と現行LLM方式の比較、推薦理由の明示。
第三段階：旅行データ整備、RAG、対話的な追質問、必要に応じて独自LLMの接続。

資料の適用範囲：2026年10月25日提供の qar-fixed.zip の静的ソース解析。公開サイトの現在の稼働、外部AIモデルの有効性、GCP上の実際のデプロイ構成までは検証していない。実装にないものを実装済みとして記載しない。
